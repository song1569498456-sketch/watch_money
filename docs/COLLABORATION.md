# 多模型与子 Agent 协作计划

本计划与《01_监控体系开发计划.md》配套使用，替换主计划中关于人员分工、验收和持续推进的对应规则。

# 多模型团队、子 Agent 分工与持续执行

## 1. 模型与角色

### 主架构师 / 开发 Leader

模型：gpt-6-astra
推理强度：high

职责：

- 理解目标，设计架构、模块边界、数据契约和验收标准。
- 拆分任务、建立依赖关系，由其发起并领导多个子 Agent。
- 指定各子 Agent 的职责、文件范围、交付物和验证要求。
- 处理跨模块设计、集成问题和技术分歧。
- 持续检查进度，分配后续任务，组织修复与集成。
- 向验收 Leader 提交完整的可运行版本和验证证据。

### 验收 Leader

模型：gpt-6-astra
推理强度：high

作为独立子 Agent，由主架构师发起。

职责：

- 根据用户需求和阶段验收标准独立检查交付结果。
- 阅读关键实现，核对测试证据，实际运行必要验证。
- 检查真实 API 接入、数据语义、页面行为、异常恢复与文档。
- 判断阶段是否通过，输出明确结论及问题清单。
- 对修复结果进行复验。

开发 Leader 负责组织交付，验收 Leader 负责确认通过。
开发子 Agent 自测通过不等于阶段验收通过。

### 开发子 Agent

模型：gpt-6.1-sol
推理强度：high

根据任务拆分，负责：

- 平台适配器
- 资产映射与数据模型
- 存储与历史回放
- 策略和利润计算
- 前端与可视化界面
- 消息通知
- 部署脚本与运行文档

完成实现后必须进行适用的自测，提交：

- 修改内容与文件范围
- 运行方式
- 测试命令和结果
- 已知问题
- 对其他模块的接口影响

### 测试子 Agent

模型：gpt-6.1-sol
推理强度：high

负责：

- 独立验证开发结果。
- 编写和执行有实际价值的单元、集成及端到端测试。
- 核对平台字段、费率周期、单位换算和数据时效。
- 检查断线重连、限流、数据缺失、重启恢复等行为。
- 为问题提供复现步骤、输入数据、预期与实际结果。
- 修复后执行回归验证。

测试子 Agent 可提出修复建议；跨模块修改由开发 Leader 协调。

## 2. 子 Agent 启动要求

主架构师使用当前环境的子 Agent 工具创建团队。

创建时显式指定：

- 模型
- high 推理强度
- 任务目标
- 工作范围
- 输入资料
- 接口约定
- 验收条件
- 交付格式

若工具要求使用独立上下文才能指定模型，则使用独立上下文，并在任务描述中补齐必要信息。

模型或并发能力不可用时，明确报告实际可用能力，不把其他模型标称为指定模型。

## 3. 并行工作与代码协作

- 根据实际并发上限安排任务，预留架构协调能力。
- 优先并行处理接口明确、文件范围独立的任务。
- 先确定共享数据契约，再并行开发依赖模块。
- 每个任务指定主要负责的目录或文件。
- 共享核心文件指定单一负责人，其他 Agent 提交修改需求。
- 不覆盖、不回退其他 Agent 或用户的未提交修改。
- 需要隔离时使用独立分支或工作树。
- 集成由开发 Leader 组织，集成后再次验证。

任务板至少包含：任务 ID、负责人、依赖、文件范围、状态、验收条件、证据链接。

任务状态：

待开始 → 开发中 → 自测通过 → 独立测试 → 待验收 → 验收通过

失败时进入：

待修复 → 修复中 → 复测 → 再验收

## 4. 标准交付闭环

每个可交付单元执行：

1. 架构师定义任务与验收标准。
2. 开发子 Agent 实现并自测。
3. 测试子 Agent 独立测试。
4. 开发子 Agent 修复问题。
5. 测试子 Agent 回归验证。
6. 开发 Leader 集成并检查整体运行。
7. 验收 Leader 独立验收。
8. 更新文档、任务状态和提交记录。
9. 自动领取或分配下一项任务。

验收 Leader 输出：

- 通过或不通过
- 检查范围
- 实际执行的验证
- 证据位置
- 阻塞问题与负责人
- 非阻塞改进项

阶段通过后，开发 Leader 自动推进下一阶段。

## 5. 持续推进要求

工作模式为持续推进，直到三个阶段完成验收，或遇到确实需要用户输入才能继续的阻塞条件。

- 不在完成计划、脚手架或局部功能后结束工作。
- 不在子 Agent 交付后只做总结；继续集成、验证和派发任务。
- 不因单个平台接入受阻而停止其他平台开发。
- 测试失败后继续定位、修复和复测。
- 验收不通过后，根据问题清单立即进入修复循环。
- 一个阶段通过后自动开始下一阶段，无需重复询问是否继续。
- 等待子 Agent 时，架构师推进接口审查、集成准备、文档核对或其他独立工作。
- 定期向用户报告实际进展、关键问题和下一步。
- 遇到凭证、权限或需求歧义，直接提出具体问题，同时继续不依赖答案的工作。

持续推进以当前运行环境的能力为边界。
会话中断、上下文切换或运行额度耗尽前，及时保存进度；没有后台运行机制时，不宣称任务仍在后台执行。

## 6. 进度持久化

docs/STATUS.md 记录：

- 当前阶段与交付目标
- 已完成任务及验证证据
- 运行中的子 Agent 与职责
- 待集成成果
- 未解决问题与复现方法
- 下一项可直接执行的任务
- 所需用户输入

恢复工作时：

1. 读取仓库指令、PLAN、STATUS 和验收记录。
2. 核对工作区与实际运行状态。
3. 复用已有有效成果。
4. 从未完成任务继续推进。

最终完成条件：

- 三个阶段达到各自验收标准。
- 验收 Leader 确认通过。
- 本地运行验证完成。
- 平台覆盖与未完成条件如实记录。
- 代码、配置样例、启动脚本和文档齐全。
